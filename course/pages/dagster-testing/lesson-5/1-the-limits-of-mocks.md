# Ограничения mock-объектов при тестировании

Подмена зависимостей помогает убедиться, что код работает ожидаемым образом. Но в инженерии данных необходимо также проверить, что код способен взаимодействовать с системами в рабочем окружении.

В этом уроке снова обновим наши ассеты: теперь будем получать данные о населении городов из базы данных. Всё это можно реализовать с помощью mock-объектов, но желательно, чтобы хотя бы часть тестов использовала реальное подключение к базе.

Использование настоящей базы позволяет выявить больше проблем до отправки кода в production, поскольку условия выполнения становятся ближе к реальным.

Кроме того, настоящая база помогает обнаружить проблемы, имитация которых с помощью mock-объектов потребовала бы значительных усилий. Например, анализатор SQL выявит синтаксические ошибки в запросах к базе. Mock-объект может не обнаружить следующую ошибку:

```sql
SELECT
   city_name,
   population
FROM data.city_population
WHERE state_name = "NY"; -- Incorrect quotation marks
```

Здесь можно воспользоваться интеграционными тестами, чтобы убедиться, что всё работает как ожидается.

## Интеграционное тестирование

Интеграционные тесты проверяют совместную работу различных компонентов системы. Они помогают выявлять проблемы в потоках данных, обмене информацией и взаимодействии объединённых частей приложения.

Обычно интеграционные тесты не выполняются непосредственно на production-системах. Вместо этого используется эквивалентное тестовое окружение.

Интеграционное тестирование может быть сложным. Однако Dagster проектировался с учётом такого рабочего процесса. Ты увидишь, насколько легко подменять различные зависимости для тестирования без изменения основной логики кода.
