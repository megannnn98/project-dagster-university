# Обзор

При материализации типа `table` dbt заменяет старую таблицу новой, построенной по модели. Однако часто нужно добавлять данные к существующим. Для этого dbt предоставляет материализацию `incremental`, позволяющую обрабатывать только выбранную новую часть данных.

Обычная инкрементальная модель может быть хрупкой:

1. **Повторный запуск не обязательно воспроизводит тот же результат.** Один запуск может добавить десять миллионов строк, а следующий — ни одной. Откатить изменения тоже непросто: границы вставляемых данных динамические и не отслеживаются dbt как отдельные партиции.
2. **Пересчёт исторических данных может потребовать `full refresh`.** Например, если источник данных за несколько прошлых запусков был неверным, а затем его исправили, типичная модель, выбирающая только новые записи, не подхватит исправления. Без дополнительной логики придётся перестраивать всю таблицу. Для больших инкрементальных моделей это долго и дорого.

Инкрементальные модели полезны, но управлять ими удобнее, когда можно предсказуемо повторять обработку конкретной части данных без полного пересчёта таблицы.

## Как помогают партиции Dagster

{% callout %}
> 💡 **Нужно освежить знания о партициях?** Посмотрите [короткое видео Dagster](https://www.youtube.com/watch?v=zfLBHFCbocE) на YouTube.
{% /callout %}

Партиции задают явные границы данных, например месяц или местоположение. Это позволяет понять, какие данные должна обработать каждая материализация, и организовать повторяемые запуски при соответствующей логике записи.

Партиции можно выполнять независимо. Если проблема затронула одну из них, достаточно повторно материализовать её, сохранив остальные части ассета.

В этом уроке создадим инкрементальную модель dbt и упростим управление ею с помощью партиционирования.
